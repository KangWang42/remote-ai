# 手机与电脑协同控制计划

目标是让同一个任务在手机与电脑之间连续使用，打开手机不改变电脑正在运行的程序，返回或断网不结束任务。完整控制以同一个运行实例为基础；恢复历史与创建副本都不作为实时同步。

## 已确认的问题

- Remote AI 自己创建的终端已经支持两个客户端连接同一进程。电脑已有的外部对话则通过扫描记录、钩子和工具消息入口接入，两者的控制能力不同。
- `can_takeover` 表示能否结束独立 CLI 进程，不能代表能否停止某次生成、关闭桌面应用中的一个标签或安全释放共享后台中的单段对话。
- Android 工作台此前没有读取 `can_takeover`，也没有调用已有的 `session_end`，导致浏览器内可以结束的独立 CLI，在 App 工作台没有对应操作。
- 手机发送接口可能只接受了排队消息；客户端没有区分排队、工具接收和记录中已出现。按“出现了其它用户消息”删除本地待发送项会把电脑端的输入误当作手机消息送达。
- 外部会话的“接管”会结束原进程再恢复历史。副本则产生独立对话，不能满足两端继续同一任务的要求。

## 交互约定

| 操作 | 用户看到的效果 | 实现边界 |
| --- | --- | --- |
| 打开 / 返回 | 查看或离开同一任务，电脑继续运行 | 只连接或断开视图 |
| 发送消息 | 明确显示发送中、已排队、工具已接收；失败保留输入 | 排队不宣称执行完成，不自动重发结果未知的消息 |
| 停止当前执行 | 终止这一轮，保留对话和原应用 | 仅在连接当前运行实例且适配器支持时提供 |
| 结束会话 | 结束所选运行实例，保留已保存记录 | 只允许已核实的独立进程，或应用提供的会话级关闭接口 |
| 隐藏 / 归档 | 改变列表展示或历史归档 | 不冒充停止或结束 |
| 接管到共享终端 | 结束外部 CLI 后在 Remote AI 终端恢复；手机和电脑随后连接同一个终端 | 单独确认中断后果；不用于共享应用进程 |
| 创建副本 | 新任务继承已有历史，原任务继续 | 明示后续不相互同步，放在次级菜单 |

常用路径为“打开任务 → 输入 → 查看执行 → 返回”。接管和副本不放在发送失败后的默认补救位置。沿用现有颜色、字号和页面结构，优先保证长对话的阅读空间、固定输入区和手机触控；操作不可用时说明原因，不用消失的输入框或必然失败的按钮代替解释。

## 外部应用的准入条件

适配器必须连接正在服务目标对话的原实例。扫描历史文件只能证明可读；消息队列只能证明可提交；独立 CLI 的进程归属只能证明可结束该进程。三者均不能推出对桌面应用的完整控制能力。

尚未核实的应用级控制不承诺可用。优先验证官方会话、执行中断、审批和关闭接口；若原应用不开放这些接口，再评估用户可见的窗口控制方案及其焦点冲突、权限和多窗口定位。不得删除写入锁、修改对话数据库、结束共享后台或启动第二个写入者来制造同步效果。

## 通道的选择与 Claude Code 的控制（2026-10-13 补充）

上面的“原应用控制链路”把 Codex 桌面通道做成了 Codex 桌面版对话的唯一入口，并去掉了 Claude 桌面版闲置时的发送。复核后调整为：一段对话可能有几条通道，按下面的顺序取可用的那条，前一条不可用时退回后一条，而不是整体不可用。

| 通道 | 提供的操作 | 适用 |
| --- | --- | --- |
| 原应用通道（`codex-desktop`） | 空闲时发送、停止指定轮次 | Codex Windows 桌面版，已核实的版本，已添加项目里的对话 |
| 工具的钩子 | 回答确认请求；执行中留言，做完后交付；下一步之前停止（Claude Code） | 两个工具的所有运行位置 |
| 工具自己的闲置入口 | 闲置时发送并唤醒 | Claude Code 的会话间消息（桌面版的对话同样登记了地址）；Codex 命令行的 `codex queue` |

- Codex 桌面版不走 `codex queue`：队列属于另一个后台，会成为同一段对话的第二个写入者。原应用通道不可用（对话不在已添加的项目里、桌面应用换了版本）时，仍可在它执行时留言，闲置时不能发，并说明原因。
- Claude 桌面版恢复闲置时的发送。它用的是 Claude Code 自己的会话间消息，由持有这段对话的那个进程接收，不产生第二个写入者。
- Claude Code 的“停止回答”：它每一步之前运行 `PreToolUse` 钩子，电脑端在手机要求停止后，对下一次回答 `continue: false`，这一轮就此结束，对话和程序保留。已在 Claude Code 2.1.283 上用本程序的钩子实测。代价是每一步多运行一次钩子（约 0.1 秒），电脑上会闪一下“running PreToolUse hook”；装上钩子之前已打开的对话要重新打开才支持。
- Claude 没有可核实的桌面原生通道（它的会话间协议只声明了 `notify_idle`、`artifact_yield`，没有中断），所以不做版本锁定的私有接口，停止走钩子。

## 统一的通道判定与两个工具同一套操作（2026-10-13 补充二）

上一节的规则原先分散写在列表和各个操作的分支里。现在由 `agent-windows/Ways.cs` 一处判定：输入是这段对话的扫描结果、钩子报告的状态和桌面应用通道的状态，输出是“发消息、停止、回答、结束”各走哪条通道，以及做不了时给人看的原因。列表和执行都用它，手机页面按 `ways` 和 `why` 显示，不再按工具名判断。新增工具或通道时只在这里加判定。

| | Claude Code（桌面版、编辑器、命令行） | Codex 桌面版（有通道） | Codex 桌面版（无通道） | Codex 命令行 |
| --- | --- | --- | --- | --- |
| 执行中发消息 | 钩子：做完后交付 | 钩子：做完后交付 | 钩子：做完后交付 | 钩子：做完后交付 |
| 闲置时发消息 | 会话间消息唤醒 | 应用通道 | 不能，说明原因 | `codex queue` |
| 回答确认请求 | 钩子 | 钩子 | 钩子 | 钩子 |
| 停止回答 | 钩子：下一步之前 | 应用通道：立即 | 不能，说明原因 | 不能；说明原因并可改为结束 |
| 结束 | 命令行里的可以 | 在应用中关闭 | 在应用中关闭 | 可以 |
| 在桌面应用新建对话 | `claude://code/new` | `codex://threads/new` | | |

- Codex 桌面版在执行时，应用通道不接收新消息（原先页面只让用户先写草稿）。现在这时发的消息经钩子留给对话，和其它执行中的对话一致；手机即使仍按应用通道提交，电脑端也按当时的状态改走钩子。
- 发消息的回答统一为 `status: accepted, sent: true, now, way`，页面只有一条发送路径；只有应用通道保留“查询发送结果”。电脑端明确拒绝的消息退回输入框，不留在对话里。
- “停止回答”在对话执行时对两个工具都显示。没有可用通道时按下去显示原因；电脑端能结束它的程序时，同时询问是否改为结束。
- Claude 桌面版的“新建项目/草稿”入口：`ClaudeDesktopAdapter` 用应用自己的链接 `claude://code/new?folder=…&q=…`（应用自带的 `ccd <文件夹>` 命令生成的就是这个链接，2.31226.1.0 的程序里核对过参数名），交给 Windows 由注册了该协议的 Claude 安装包处理；只在安装包声明了这个协议、且用户没有把它改给别的程序时提供。应用拒绝网络路径，适配器在登记操作之前就拒绝。两个应用的适配器共用 `LinkedDesktopApp`（查找安装包、校验文件夹和草稿、登记回执），各自只写链接和启动方式。
- Codex 命令行的停止，两条路都在真实的 Codex 0.162.1 上试过，都不可行：一步之前的钩子回答 `continue: false`，Codex 报“PreToolUse hook returned unsupported continue:false”并继续执行；终端窗口里的对话不在共享后台服务（app-server daemon）加载的对话之列，另一个客户端读到的是 `notLoaded`，无从中断它的轮次。因此命令行里的 Codex 只提供结束和接到手机终端，原因写在窗口里。

检查：`tests/ways_check.py`（判定表，两个工具并列）、`tests/desktop_adapter_check.py`（两个链接、按工具打开、执行中改走钩子）、`relay/test_relay.py`（按工具放行、`ways` 与 `why` 的转发）、`tests/ways_ui_check.py`（真实页面和中转，电脑端由测试扮演：两个工具的发送、停止、结束、原因和桌面入口）。

仍未完成：物理手机上的验收；在真实的 Claude 和 Codex 桌面应用上打开项目、发送和停止的验收（检查里由替身扮演，没有打开真实应用）。

## 实用性复核（2026-10-13）

结论：按动作选择通道的方向可保留，但不能认定已完成完整应用远控。判断生产力的标准是离开电脑后能否独立推进任务，并在断线、并发输入和应用升级时知道每条指令的真实结果。

本轮已修复：原生发送在忙碌时转钩子，必须仍在原操作的持久回执范围内执行；回执先于通道选择，重复请求不能因为通道变化再次投递。专项回归覆盖已原生发送后转忙碌、转钩子后的查询、恢复空闲后的重试，以及重建回执服务、通道丢失后的查询。原生发送记录增加当前标签刷新恢复，不保存普通草稿或为钩子/唤醒操作假设可靠回执。未知桌面工具的检查返回稳定的业务错误。

| P0 消息可靠性 | `Reach.Open.Queued` 是内存字符串；`Say` 合并多条消息，`Taken` 按会话清空；`deliver` 将非原生异常当作未发送。并发唤醒、断线和重启尚不能逐条追踪 | 为每条指令保留操作编号、目标会话、排队状态和回执；电脑端维护顺序队列，查询不重新执行；只有确认未投递才能换通道 | 同文两条、电脑手机同时输入、回执丢失、两次并发唤醒和重启均不重复、不覆盖；未确认操作明确展示 | 待实施 |
| P1 新建任务闭环 | `LinkedDesktopApp.Open` 仅返回 `handed_off`，没有会话编号和应用完成事件，用户仍须在电脑发送草稿 | 支持的应用增加创建结果关联和回读，确认目标后再发送；只能交草稿时明确提示需要电脑操作。离线办公场景优先提供现有共享终端入口 | 仅使用手机选项目、新建、发送、收到回复，回电脑仍是同一会话 | 待真实接口核验 |
| P1 停止与队列协调 | `StopAsked` 与 `Queued` 独立；停止轮次没有暂停排队指令的统一语义；Claude 钩子不能中断正在运行的命令或纯文本生成 | 区分“下一步前停止”“立即停止本轮”“暂停后续任务”；停止时保留并暂停队列，让用户选择继续或撤回；桌面标签关闭与进程结束分开 | 留两条消息后停止，不自动开始下一项；不丢消息、不结束共享后台 | 待实施与应用实测 |
| P2 延迟与负载 | `CodexDesktopSessions.Refresh` 对最多 20 个会话逐个握手和取快照，最多两个并行；缓存 15 秒，单次超时 8 秒；前端还轮询记录 | 按应用维护连接，利用已验证的广播更新活动会话；前台优先、失败退避、历史惰性读取，保留断线重建 | 20 个以上会话含失效实例时，前台能力不反复失效；记录延迟、请求数和 CPU 变化 | 待实施 |

统一调度应保留用户意图和操作身份，适配器只负责能力发现、执行、观察和错误分类。优先补齐以上闭环，再考虑更多应用入口。不要通过第二个写入者、强杀共享进程或不可确认的自动重发制造“同步”。本轮验证覆盖隔离适配器和真实浏览器中的模拟应用；不替代物理 Android 与两个真实桌面应用的往返验收。
